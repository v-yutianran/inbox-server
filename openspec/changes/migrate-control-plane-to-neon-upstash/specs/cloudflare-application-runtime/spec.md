# Spec Delta

## MODIFIED Requirements

### Requirement: D1 持久化与版本迁移
系统 MUST 以版本化迁移管理 Neon PostgreSQL 的权威业务结构，并 SHALL 将现有 D1 与旧持久卷中需保留的全部长期业务状态及历史记录迁入 Neon。迁移 MUST 保留稳定主键、关联关系、任务信封、幂等标识和终态；不同来源的主键冲突或语义等价性未证实时 MUST 保留可追溯的原始记录，MUST NOT 覆盖现有业务行或自动重放旧队列项。Upstash Redis MUST 仅保存可重建的短期状态。D1 在切流后 MUST NOT 接收新的权威业务写入。

#### Scenario: 空数据库应用迁移
- **WHEN** 对空目标 schema 依序应用全部迁移
- **THEN** 所有业务表、约束与迁移记录可用，且不影响数据库中不属于本服务的对象

#### Scenario: 重复导入稳定快照
- **WHEN** 对同一冻结的 D1 快照重复执行导入与核对
- **THEN** Neon 的稳定主键集合、记录数、关联关系和关键不变量保持一致且不产生重复记录

#### Scenario: 旧持久卷与 D1 存在差异
- **WHEN** 旧 PostgreSQL 记录或 Redis 队列项不能证明已由 D1 完整覆盖
- **THEN** 差异须被逐项计数并可恢复地保存；存在主键冲突或身份未知的队列项不得静默丢弃、覆盖权威行或自动触发外部副作用

#### Scenario: 跨表状态原子更新
- **WHEN** 一次任务完成、重试或死信重放需要改变多个持久记录
- **THEN** Neon 要么提交全部相关变更，要么不提交任何相关变更

#### Scenario: 临时状态依赖失败
- **WHEN** Upstash 暂时不可用或短期键过期
- **THEN** 已确认任务、凭据、效果记录及重放材料仍可由 Neon 恢复，不因 Redis 失效而丢失

### Requirement: 可回滚切换
系统 MUST 在生产切换前完成 D1 与旧持久卷的覆盖/差异、计数、主键和关键不变量核对，禁用副作用的 shadow 运行、幂等验证和回退演练；任一门槛失败时 SHALL 保持当前权威路径运行。切流后若需回退，MUST 先停止新路径的业务写入并核对切流后的增量，禁止在存在未处理增量时将旧 D1 当作完整权威副本。

#### Scenario: 迁移门槛未通过
- **WHEN** 数据计数、主键、关联、任务结果、凭据解密或幂等检查任一失败
- **THEN** 系统不得切换权威数据源或启动新的业务副作用路径

#### Scenario: 切换后发现异常
- **WHEN** 新运行路径在观察期出现重复分发、数据缺失或持续健康失败
- **THEN** 运维人员可以停止新业务写入，核对并回补切流后增量，再将读写流量恢复到经过验证的路径
